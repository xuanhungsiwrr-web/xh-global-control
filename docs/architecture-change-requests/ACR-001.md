## Trigger

that the example command in the specification exists.

was the user-installed Claude Desktop Local Agent plugin `xh-tuvan` version

was a Claude skill bundle, not an importable Python package or executable

The configured command `python -m xh_tuvan` was checked in the repository virtual
environment: no module, package metadata, or `xh-tuvan`/`xh_tuvan` command exists.
Follow-up review on 2026-09-09 found the personal Codex plugin `xh-tuvan`
version `0.7.3`, installed and enabled from `C:\Users\xuanh\plugins\xh-tuvan`.
A fresh authenticated Codex 0.153.4 process successfully discovered and loaded
the `xh-tuvan` skill. The plugin manifest declares an empty `capabilities`
array, however, and both its README and `references/runtime-openai.md`
explicitly state that it is a skills-only port, not an MCP server or executable
TaskEnvelope bridge. No PluginResult transport is declared. The plugin's four
unit tests pass, but they cover a NotebookLM import script rather than the Global
Control integration contract.

## Current specification

The current M4 architecture requires all of the following:

1. `XHTuvanAdapter.execute(task: TaskEnvelope) -> PluginResult` remains the
   `DomainPluginAdapter` contract.
2. Global resolves a concrete subscription `ExecutionChannel` and worker before
   plugin execution.
3. `xh-tuvan` invokes the resolved Claude Code or Codex channel while retaining
   ownership of its domain workflow.
4. Global receives artifact references and operational metrics in `PluginResult`.
5. At the time of the original conflict, `config/plugins.yaml` described:
   `python -m xh_tuvan`.

## Conflict

Neither the original Claude bundle nor the installed Codex skills-only plugin
exposes the configured process entry point or a machine-readable
TaskEnvelope/PluginResult transport. The existing `DomainPluginAdapter.execute`
signature also contains no execution-context value for the already-resolved
channel, worker, permission grant, or budget grant.

Inventing any of the following inside Global would silently change a contract or
ownership boundary:

- treating a Claude skill bundle as a Python process;
- sending an unconstrained prompt to Codex and treating skill discovery as a
  completed TaskEnvelope/PluginResult execution contract;
- encoding domain instructions from `SKILL.md` in Global;
- extending `TaskEnvelope` or `DomainPluginAdapter.execute` without approval;
- bypassing the resolved channel, permission, or budget decisions;
- synthesizing `PluginResult` usage, cost, or artifacts when the plugin did not
  return them.

Therefore the real-plugin bridge and M4 end-to-end exit criterion cannot be
implemented faithfully from the supplied executable contracts.

## Options considered

1. Provide a versioned `xh-tuvan` process wrapper in the plugin repository. It
   would read one TaskEnvelope JSON document, receive an opaque execution-context
   reference, invoke the supplied channel bridge, and write one PluginResult JSON
   document. This preserves the current Global plugin interface.
2. Add a formal skill-bundle entry-point type and a versioned infrastructure
   adapter capable of invoking the Codex or Claude Desktop/Cowork plugin runtime.
   This requires an explicit transport for TaskEnvelope, resolved channel,
   permission, budget, cancellation, and PluginResult.
3. Change `DomainPluginAdapter.execute` or `TaskEnvelope` to carry execution
   context directly. This is the widest contract change and would affect every
   plugin, schema, and boundary test.
4. Copy the plugin's domain instructions into Global or translate them into a
   Codex prompt. Rejected because it violates the domain-ownership boundary.

## Recommended change

Choose option 1: add a thin, versioned process wrapper owned by the `xh-tuvan`
repository, not by Global Control. Keep domain logic in the existing skill bundle.
Define a minimal transport specification with:

- TaskEnvelope JSON on stdin (or a path to an immutable envelope artifact);
- opaque execution context containing the selected channel id and an executable
  channel-bridge reference, plus granted permission/budget limits;
- PluginResult JSON on stdout (or a path to an immutable result artifact);
- stdout reserved for the result document and diagnostics sent to stderr;
- explicit healthcheck and cancellation behavior;
- truthful nullable/absent usage fields where the execution surface does not
  report token counts or cost.

Global's `XHTuvanAdapter` can then implement the existing interface without
learning the plugin workflow. The wrapper may internally invoke the installed
skills through a supported Claude runtime, but that mechanism remains plugin
owned.

## Consequences

- M4 remains `BLOCKED` until the wrapper/runtime is supplied and its invocation is
  verified on an authenticated subscription channel.
- Unaffected Global components (worker capability selection, generic channel
  execution, artifact/cost/operational persistence, and boundary tests) may be
  completed without claiming real xh-tuvan execution.
- The transient Claude Local Agent cache path must not become a production
  configuration dependency; a stable installed path or runtime identifier is
  required.
- The approved work adds a plugin-owned `bridge/` directory to the stable source;
  existing skill workflow and the desktop plugin cache remain unchanged.

## Scope impact

Affected and stopped:

- real `XHTuvanAdapter` invocation;
- real xh-tuvan `PluginResult` return;
- the M4 real domain-task acceptance scenario.

Unaffected:

- `ExecutionChannelAdapter` implementations;
- `WorkerSelector` and required-capability checks;
- task/attempt/event/artifact/cost/global-learning persistence;
- generic-plugin boundary tests and process-adapter contract tests using a
  protocol fixture that is explicitly not acceptance evidence.

## Original decision request (Option 1 now approved)

Provide or approve one executable bridge:

1. the recommended xh-tuvan process wrapper and its stable path/version; or
2. a documented Codex/Claude Desktop/Cowork plugin-runtime API plus approval for
   the formal skill-bundle entry-point contract.

Also provide a real isolated project workspace that satisfies xh-tuvan's own
prerequisites if the acceptance task is expected to create project output.
